# Project general coding standards

## General guidelines
- Never include "Generated by Copilot" in any generated code

## Naming Conventions
- Use PascalCase for component names, interfaces, and type aliases
- Use lowercase for variables, functions, and methods; separated by underscores
- Prefix private class members with underscore (`_`)
- Use `ALL_CAPS` for constants

## Error Handling
- Use `try/catch` blocks for async operations
- Implement proper error boundaries in `React` components
- Always log errors with contextual information

## Code style
- Never use any emoji icons in the code
- Use two-character variable names like `ix`, `jx` for indexing to improve clarity
- Add '#end of <function>' after every function

## Indentation
- Use 2 spaces for indentation, fix all files created to that standard
- Replace all tabs with spaces, if modifying existing code
- Remove all trailing spaces at the end of each line in a file.

## Temporary files
- Remove any temporary files or directories created, that are used by the agent for validation

## File Headers
- All code files must include comprehensive headers in a multi-line comment block
- Header format varies by language but must include:
  - Shebang line (for executable scripts): `#!/usr/bin/env python3` or `#!/usr/bin/env bash`
  - Multi-line comment block with:
    - Filename with relative path from project root
    - Date in format "DD MMM YYYY" (e.g., "02 Aug 2025")
    - Author with full name and email in parentheses
    - Detailed description of file functionality and purpose
    - Usage examples (for CLI tools and scripts)
    - Reference links (if applicable)
- Python files: Use triple-quoted docstring with `#` prefix for each line
- Shell scripts: Use `#` comment blocks
- JavaScript/TypeScript: Use `/**` multi-line comment blocks

## Shell Scripts
- Always use `#!/usr/bin/env bash` as the shebang line for portability
- Include comprehensive header comments with:
  - Filename with relative path from project root
  - Date in format "DD MMM YYYY"
  - Author with email
  - Detailed description of script functionality
- Use `set -euo pipefail` for strict error handling
- Quote all variables to prevent word splitting: `"$variable"`
- Use `[[ ]]` for conditional tests instead of `[ ]`
- Add comments explaining complex logic or API calls
- Use meaningful variable names in UPPER_CASE for environment variables
- Validate required environment variables with `${VAR:?error message}`
- Add usage information and help text for scripts with parameters

## Python Scripts
- Follow PEP 8 style guidelines
- Include comprehensive docstrings for all functions and classes
- Use type hints for function parameters and return values
- Include header comments with:
  - Shebang: `#!/usr/bin/env python3`
  - Triple-quoted docstring with `#` prefixed lines containing:
    - Filename with relative path from project root
    - Date in format "DD MMM YYYY"
    - Author with full name and email
    - Detailed description of script functionality
    - Usage examples for CLI tools
    - Reference URLs if applicable
- Use `if __name__ == "__main__":` for script entry points
- Handle exceptions gracefully with specific exception types
- Use `pathlib.Path` for file system operations instead of `os.path`
- Add logging configuration for debugging and monitoring
- Use f-strings for string formatting
- Import statements should be grouped: standard library, third-party, local imports
- Add `#end of <function>` comment after each function definition

## README Files
- Create comprehensive README.md files for tools, scripts, and modules
- Include the following sections in order:
  - **Title**: Clear, descriptive title of the tool/project
  - **Description**: Brief overview of what the tool does
  - **Features**: Bullet-pointed list of key capabilities
  - **Installation**: Dependencies and setup instructions
  - **Usage**: Multiple usage examples from basic to advanced
    - Basic usage example
    - Command line arguments example
    - Configuration file example
    - Environment variables example
  - **Configuration**: Detailed explanation of config files and options
  - **Examples**: Real-world usage scenarios with sample commands
  - **Troubleshooting**: Common issues and solutions
  - **API Reference**: For libraries and modules
  - **Contributing**: Guidelines for contributions (if applicable)
- Use proper Markdown formatting with code blocks, tables, and lists
- Include actual working command examples that users can copy-paste
- Provide sample configuration files and expected outputs
- Use clear, concise language suitable for technical users

## Requirements Files
- Create `requirements.txt` for Python projects with external dependencies
- Use semantic versioning with minimum version specifiers (e.g., `>=2.25.0`)
- List dependencies in alphabetical order for consistency
- Include only direct dependencies (not transitive dependencies)
- Use specific version constraints for production-critical dependencies
- Format: `package_name>=minimum_version`
- Include comments for non-obvious dependency purposes when needed
- Place requirements.txt in the same directory as the main Python scripts

## File Naming Conventions
- **README files**: Use `README.md` for general project documentation
- **Specific tool READMEs**: Use `README_<toolname>.md` format (e.g., `README_bmcquery.md`)
- **Requirements files**: Always use `requirements.txt` for Python dependencies
- **Configuration files**: Use descriptive names with appropriate extensions:
  - JSON configs: `<tool>_config.json`, `<env>_config.json`
  - Environment files: `<tool>_env.sh`, `.env`
- **Script files**: Use descriptive names that indicate functionality:
  - Python: `<action><object>.py` (e.g., `json2csv.py`, `bmcquery.py`)
  - Shell: `<action>_<object>.sh` (e.g., `query_incidents.sh`, `get_field_names.sh`)
- **Output files**: Use descriptive names with timestamps when appropriate:
  - Data files: `<source>_<type>_<date>.json` (e.g., `helpdesk_incidents_2025-08-02.json`)
  - Log files: `<tool>_<date>.log`
